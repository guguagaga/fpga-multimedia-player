# 源码组织与编写约定

## 文件头注释

自有模块的文件头直接说明职责，按需要补充数据格式、握手、时钟复位或延迟约定，通常控制在3～8行。简单模块用一两句即可。端口旁说明单位和有效条件，复杂协议在相关实现处解释，构建与使用步骤统一放在docs。

删除重复用途字段、装饰横幅、开发经过及旧实现比较；数值须与现行参数一致。版权、许可、原作者信息、厂商生成标记和综合指令完整保留。

2026-11-02实际查阅了[Microsoft ONNX Runtime C++ API头部](https://github.com/microsoft/onnxruntime/blob/660125b35916c134c00bc746c34503321e17150f/include/onnxruntime/core/session/onnxruntime_cxx_api.h)（文件修改提交日期2026-10-08）和[AMD/Xilinx Unisim BUFG模型](https://github.com/Xilinx/XilinxUnisimLibrary/blob/c587d2310c2315cbe2d01de0bbbc91974cd25915/verilog/src/unisims/BUFG.v)（文件修改提交日期2020-06-25）。前者把简短概述与必要的接口契约放在一起；后者属于厂商器件模型，保留法律声明和器件语义。上述规则取其清晰、准确和维护接口约定的做法，不将个别仓库格式视为厂家的统一规范。

本轮精简36个文件的说明性注释，净减少289行；全部92个RTL文件的非注释代码和受保护注释核对通过，详见evidence/header_cleanup.json与evidence/comment_cleanup.json。

## 实现与维护

参考 lowRISC Verilog Coding Style Guide 和 Google Python Style Guide 的模块划分、显式接口、命名一致性与可审查性原则。查阅日期为 2026-11-02：

- https://github.com/lowRISC/style-guides/blob/master/VerilogCodingStyle.md
- https://google.github.io/styleguide/pyguide.html

本工程使用厂商工具支持的 Verilog，并混合已有模块与新增逻辑，不能宣称完全符合上述项目规范。提交前按以下维度检查：

| 维度 | 当前实现和要求 |
|---|---|
| 模块职责 | RTL 按功能目录划分；顶层负责连接与调度，各流水级采用明确握手 |
| 时序语义 | 寄存器更新使用非阻塞赋值，组合计算明确默认值；跨域使用既定同步器/FIFO |
| 接口说明 | 简短说明设计意图、边界条件及所防止的问题；注明复位极性、事务生命周期、背压、缓存所有权和水位单位 |
| 命名 | 新模块优先小写下划线，状态/参数使用可识别名称；保留既有接口避免破坏工程绑定 |
| Python 入口 | argparse 参数检查、main 入口、路径显式传入，失败返回非零状态 |
| 配置和数据 | 时序、引脚、初始化数据及码表独立保存并由哈希清单绑定 |
| 验证 | 修改前后记录输入、工具与测试范围；功能或约束修改后重新综合及签核；纯注释修改核对非注释代码及综合指令 |
| 第三方 | 保留原作者、版权和许可，原厂受保护 IP 按清单独立存放，完整保留原版权与加密内容 |

本次审查确认目录边界和清单可追溯，交付入口使用包内相对路径。RTL 注释已精简为当前设计的用途、边界与保护条件，删除版本比较和调试经过。逐文件核对非注释代码与综合指令，结果见 `evidence/comment_cleanup.json`。顶层文件较长，部分 Python/C++ 实现存在紧凑写法、缩进及行长不统一；本次未全局重排代码，也未将风格审查表述为完全符合外部规范。

新增和维护代码以四空格 Python 缩进、显式错误消息、避免副作用导入为准。RTL 的格式调整也应单独提交并先做等价检查，不能将大范围改名和功能修复混合。对外报告只描述现有实现及验证证据。
